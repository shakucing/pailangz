## Integrations and limitations

The numbered, opponent-labelled game score inputs replace the JSON editor in all 192 fixture forms. Browser checks cover a valid zero score, a split BO3 series, adding/removing the deciding game, automatic winners for either side, tied-game feedback and blocking an extra game after the series is won. The 390 px view has no document overflow. The existing unconfirmed scoring/draw rules are displayed with an explanation and prevent submission; UI verification did not submit official match results. TypeScript, all 59 unit tests and the optimized production build pass. [Desktop score entry](screenshots/game-score-entry-desktop.jpg), [phone score entry](screenshots/game-score-entry-mobile.jpg).

- Google Forms/Sheets sync remains disconnected. The supplied question headers configure CSV import; a verified responder URL and authorized integration credentials are still needed. The later 65-row CSV was used to reconcile IGN listing numbers; private registration fields were not copied or exposed by that reconciliation.
- Production hosting, managed PostgreSQL, separate preview resources, S3 access controls, Vercel secret configuration, deployment protection, backups and restoration require operator setup. Local PGlite uses a synthetic-only owner connection; deploy with the non-owner `pailangz_app` role and native PostgreSQL.
- Tournament dates, game title, eligibility/mapping, actual four-player team rosters and the listed competitive rules still require explicit admin confirmation. No official results or dates are fabricated. Qualification and brackets are generated only after confirmed rules and current frozen rankings.
- Game scores have numbered numeric inputs and automatic series winner calculation. Rules, initial configuration and bracket seeding still use validated JSON forms; draft size edits have a numeric editor. Capacities, league rounds/match quotas, qualification pools/slots and power-of-two brackets are configurable (2–256 entrants). Even leagues support a non-repeating subset of rounds; the explicit balanced odd-count policy requires a complete N-round cycle with one bye each. Other odd-cycle policies and a drag-and-drop designer are not implemented.
- Controlled revision resolution supports an explicit admin-approved restart with old results retained in archived history and excluded from new standings. It does not transfer old scores into regenerated fixtures. Historical stages are read only; entrants and result/evidence records are preserved.
- Staff logins require email and password. The user explicitly requested removal of the authenticator after the original implementation; MFA is no longer configured. Provisioning uses the documented operator CLI. QA accounts use random temporary credentials, are suspended after checks, and have their sessions revoked. There are no public default credentials.
- Optional English content is authored by staff; missing English versions fall back to the original content. IGNs are never translated.
- Evidence is private and encrypted. File signatures and sizes are checked; full decoding/malware scanning and public evidence publishing are not implemented.
- Encryption key rotation/re-encryption, irreversible personal-data deletion and retention automation are documented operator processes, not automatic jobs. Complex rollback of already-started tournament matches remains an explicit operator decision.
- Business state/audit writes are atomic. Failed authenticated API operations record redacted failure events when the database is available. A database outage may prevent both the operation and its failure event; external operational monitoring remains a production responsibility.
- Append-only application audit controls are not protection against a database superuser disabling triggers. Production needs independently retained logs/backups. This verification is not a penetration test or security certification.

## Commands

```sh
pnpm typecheck
pnpm test
pnpm test:integration
pnpm build
# With the synthetic local database and built web server running:
pnpm test:web
```

`test:integration` creates and removes an isolated temporary database. By default it uses PGlite. Set `TEST_PG_BIN_DIR` to an installed native PostgreSQL `bin` directory for real concurrent connections; the runner starts a separate temporary cluster on a free port and never uses an existing database.
